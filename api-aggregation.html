高达 C 端首屏渲染优化 · 接口聚合方案

境外业务场景：用户在海外（如沙特），服务器在香港 —— 把组件级的多次跨境串行请求，聚合为主接口内的一次服务端内网并发调用

为什么在高达场景收益大？普通场景下「用户→服务器」和「服务器→服务器」差别不大；但我们是境外业务 —— 用户在沙特、服务器在香港。把 N 次「沙特 ⇄ 香港」跨境请求，收敛为 1 次跨境 + N 次香港内网调用，省下的就是 (N-1) 次跨境 RTT。

核心难点前端如何描述请求参数给后端？— 构建时转换

每个组件仓库内有一个固定命名的 apiAgg.js，组件构建时由 Node.js 构建服务 sailor-gundam-build-server 顺便完成 JS → Groovy 编译，随构建产物一起交付：

① 前端书写 apiAgg.js

组件的参数构造逻辑本来就写在前端代码里（高达后端不了解业务组件的下游参数），前端同学用熟悉的 JS 描述，放在组件仓库固定文件中

// 组件根目录 / apiAgg.js params: { cityId: ctx.env.cityId, lng: ctx.env.longitude, tab: ctx.urlQuery.tab }
→

② 构建时编译 · build-server

sailor-gundam-build-server（Node.js）构建组件、上传 CDN 的同时，调用自研 js-to-groovy 把 apiAgg.js 编译成 Groovy，传给高达后端与组件配置绑定存储

组件 bundle → CDN apiAgg.js → Groovy → 高达后端 github.com/pbgf/js-to-groovy
→

③ 运行时执行（Groovy）

主接口命中页面后，高达后端取出各组件绑定的 Groovy 脚本，注入同构上下文执行，得到下游请求参数，发起内网聚合调用

def params = [ cityId: ctx.env.cityId, lng: ctx.env.longitude, tab: ctx.urlQuery.tab ]
为什么选 Groovy？

对比社区方案 JSONPath / SpEL / JEXL 等，Groovy 在成熟度、性能、扩展能力上综合最优 —— 表达力足以覆盖真实的参数构造逻辑（条件、循环、函数调用），而非纯取数。

为什么自研 js-to-groovy？

前端直接写 Groovy 门槛高、易出错，社区没有成熟的 JS → Groovy 转换方案。自研后前端只写 JS，降低书写与维护成本。

为什么是前端来写？

下游服务的参数构造逻辑属于业务组件的实现细节，代码在前端。高达后端作为通用聚合层，不感知业务逻辑，只负责执行与转发。

关键保障上下文同构：前后端语义一致

同一段参数构造逻辑，前端本地执行（降级/旧链路）与后端 Groovy 执行（聚合链路）必须产出相同结果 —— 依赖三类上下文在两端保持一致：

① 运行时环境

国家、城市、语言、经纬度等

✓ 主接口请求时前端原本就会上传给后端，两端天然同源
② URL 参数

页面 URL 上的 query 参数

✓ 随主接口请求一并传递，两端取值一致
③ 页面 & 组件配置

页面配置、组件配置信息

✓ 配置本来就是高达后端下发给前端的，天然保持一致
